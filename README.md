# Web Security Lab — разбор уязвимостей на учебных стендах

Практический разбор веб-уязвимостей из OWASP Top 10. Каждый стенд — намеренно уязвимое приложение, которое я поднимаю локально, эксплуатирую, а затем показываю исправление. Цель — не только найти дыру, но и объяснить корневую причину и защиту на уровне кода.

> Все стенды написаны мной и запускаются только локально (`127.0.0.1`). Атаки проводятся исключительно на собственных учебных приложениях.

**Стек:** Python (http.server, sqlite3), Burp Suite Community, ручной анализ HTTP.

## 1. SQL-инъекция: обход аутентификации

**Уязвимость.** Форма логина строит SQL-запрос конкатенацией пользовательского ввода:

```python
query = "SELECT login, secret FROM users WHERE login = '%s' AND password = '%s'" % (login, password)
```

**Эксплуатация.** В поле логина:

```
admin' --
```

Запрос превращается в:

```sql
SELECT login, secret FROM users WHERE login = 'admin' --' AND password = '...'
```

Апостроф закрывает строковый литерал, `--` комментирует проверку пароля. Вход выполнен под `admin` без знания пароля. Второй вектор — `' OR '1'='1' --` — вход под произвольным пользователем; из-за `fetchone()` возвращается первая строка. Здесь же важен приоритет операторов: `AND` связывает сильнее `OR`.

**Корневая причина.** Пользовательский ввод смешан с телом SQL-команды — СУБД не отличает данные от кода.

**Исправление.** Параметризованный запрос:

```python
query = "SELECT login, secret FROM users WHERE login = ? AND password = ?"
row = DB.execute(query, (login, password)).fetchone()
```

На Java — `PreparedStatement` с `setString()`. Ввод передаётся отдельно от шаблона и всегда трактуется как значение.

## 2. Частичная защита: инъекция в забытом параметре

Логин защищён параметризацией, но поиск пользователей собран конкатенацией:

```python
sql = "SELECT login, secret FROM users WHERE login LIKE '%" + q + "%'"
```

`admin' --` в логине больше не работает — защита корректна. Но поиск уязвим к `' OR '1'='1' --`, что выгружает все учётные записи.

**Вывод.** Защиту применяют неравномерно: закрыли очевидную форму, забыли соседнее поле. Проверять нужно каждую точку ввода.

## 3. UNION-инъекция: доступ к сторонним таблицам

Тот же уязвимый поиск (2 колонки). В базе — отдельная таблица `api_keys`, к которой поиск не обращается.

```
' UNION SELECT name, token FROM api_keys --
```

`UNION` подклеивает вторую выборку к результату поиска при совпадении числа колонок. В ответе появляются платёжные и облачные ключи — выход за пределы бизнес-логики функции. Критический уровень.

**Исправление.** Параметризация устраняет вектор; дополнительно — принцип минимальных привилегий у учётной записи БД.

## 4. Reflected XSS

Параметр подставляется в HTML без экранирования:

```python
greet = "<h3>Privet, " + name + "!</h3>"
```

Ввод `<b>текст</b>` рендерится как разметка. Подтверждение выполнения JavaScript:

```html
<img src=x onerror="document.body.style.background='red'">
```

Боевой вектор — кража сессии через `document.cookie`, доставляемая жертве ссылкой `/hello?name=...`; код исполняется в её браузере с её куками.

**Корневая причина.** Та же, что у SQLi: данные пользователя смешаны с кодом, здесь — с HTML.

**Исправление.** Экранирование вывода (`<` → `&lt;`), флаг `HttpOnly` на сессионных куки, Content-Security-Policy.

---

## Выводы

| Уязвимость | Корневая причина | Защита |
|---|---|---|
| SQLi | ввод смешан с SQL-командой | параметризованные запросы |
| UNION SQLi | то же + избыточные привилегии БД | параметризация + least privilege |
| XSS | ввод смешан с HTML | экранирование вывода, CSP, HttpOnly |

Общий принцип всех инъекций: **пользовательские данные не должны интерпретироваться как код.** SQLi закрывается на входе в СУБД, XSS — на выходе в разметку.
